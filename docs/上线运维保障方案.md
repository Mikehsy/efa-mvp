# 上线运维保障方案（云端 SaaS 版）

- 版本：`2026-11-18-v1`
- 适用形态：Streamlit Community Cloud + Supabase PostgreSQL + GitHub `main` 分支
- 责任边界：DEV 提供技术方案、检查表、模板与故障处置建议；运营方/运维负责实际执行、证据留存、责任签字
- 配套：
  - `docs/每日巡检表.md`
  - `docs/备份与恢复演练记录模板.md`
  - `docs/安全事件应急预案.md`
  - `docs/观察期问题登记表.csv`
  - `docs/上线前自检清单.md`
  - `docs/StreamlitCloud部署指南.md`

---

## 1. 保障目标

保障系统正式上线后可稳定、可回滚、可追踪、可恢复：

| 目标 | 含义 |
| --- | --- |
| 可访问 | Streamlit Cloud 应用可正常打开、登录、进入业务页 |
| 可读写 | Supabase 数据库连接正常，账号隔离有效，数据写入成功 |
| 可验证 | 每日巡检、冒烟验收、问题处理均有记录 |
| 可回滚 | 发布前保留上一版本 commit，异常时可 `git revert` 后 Reboot |
| 可恢复 | Supabase 备份与异地备份存在，且恢复演练成功 |
| 可追踪 | 故障、变更、问题、证据按编号归档 |

---

## 2. 技术边界

当前形态下，运维保障依赖三层：

```text
GitHub main 分支：代码版本与回滚基线
Streamlit Cloud：应用运行与 Secrets
Supabase PostgreSQL：业务数据持久化
```

必须注意：

- Streamlit 容器临时盘不可依赖；`logs/*.log` 重启可能丢失。
- 关键合规事件已写入数据库 `consents` 表。
- 业务审计日志若需长期留存，必须外接日志或定期导出。
- 免费版 Streamlit 会休眠，首次访问变慢属正常现象。
- 当前无自动告警，需按 `docs/每日巡检表.md` 人工巡检。

## 3. 发布与回滚

### 3.1 发布前

1. 本地执行：

```powershell
cd "C:\Users\10692\CodeBuddy\20261113101802"
& ".\.venv\Scripts\python.exe" -m unittest discover -s tests -t . -q
```

2. 确认全量测试通过。
3. 在 GitHub 确认 `main` 分支为唯一发布源。
4. 记录当前稳定 commit：

```powershell
git rev-parse HEAD
```

5. 将该 commit 写入变更记录或当日巡检表，作为回滚基线。

### 3.2 发布后

1. Streamlit Cloud 自动部署或手动 `Reboot app`。
2. 完成 8 步冒烟：
   - 打开首页；
   - 注册/登录；
   - 录入运动员；
   - 录入测试成绩；
   - 查看数据分析；
   - 生成报告；
   - 隐私与账号导出；
   - 重启后确认数据仍在。
3. 验证三段式评分关键值：
   - 握力男成年：22kg=0，33kg=60，38.5kg=80，44kg=100；
   - 30米男 U18：4.45=60，4.34=80，4.23=100；
   - 30米男成年：4.60=60，4.34=88.1，4.23=100。

### 3.3 回滚触发

出现以下任一情况，进入回滚评估：

- 应用白屏或无法登录；
- 数据库连接失败；
- 账号隔离失效；
- 评分结果明显错误；
- 用户数据丢失或错乱；
- 安全事件需要立即下线或停用入口。

### 3.4 回滚步骤

1. 记录问题截图、时间、影响范围。
2. 找到上一稳定 commit。
3. 在 GitHub 执行 `git revert` 或将 `main` 恢复至上一稳定 commit。
4. Streamlit Cloud `Reboot app`。
5. 重新执行冒烟验收。
6. 在 `docs/观察期问题登记表.csv` 记录回滚原因、执行人、验证结果。

## 4. 日常监控

### 4.1 每日检查

按 `docs/每日巡检表.md` 执行，至少包括：

- Streamlit 应用是否能打开；
- 登录与核心页面是否正常；
- Supabase 项目状态是否为 Active；
- 是否能新增/读取一条测试数据；
- 两账号隔离抽检是否正常；
- Streamlit Logs 是否有新增 ERROR；
- 当日问题是否登记。

### 4.2 每周检查

- 本地全量回归执行一次；
- 汇总观察期问题登记表；
- 检查 GitHub `main` 分支是否有未经确认的变更；
- 检查 Secrets 是否被误提交；
- 检查 Supabase 空间使用量。

### 4.3 每月/每季度检查

- 备份恢复演练一次；
- 权限复核一次：GitHub、Streamlit Cloud、Supabase；
- 复查 PIPL E3–E11 证据是否仍有效；
- 政策版本或实际处理活动变化时，通知法务重新审阅。

## 5. 备份与恢复

### 5.1 备份对象

| 对象 | 存储位置 | 说明 |
| --- | --- | --- |
| 代码 | GitHub `main` + tag | 版本与回滚基线 |
| 业务数据 | Supabase PostgreSQL | 当前系统真实数据源 |
| 同意记录 | Supabase `consents` 表 | 合规留痕，注销后仍保留去标识化记录 |
| 配置 | Streamlit Cloud Secrets | 不纳入普通备份，离线留存关键项 |
| 本地脚本 | 项目 `scripts/` | 单机历史部署脚本，云端仅作参考 |

### 5.2 备份要求

- Supabase 开启自动备份或 PITR（视套餐能力）。
- 关键表定期导出到异地私有存储：`users`、`user_data`、`consents`。
- 备份文件必须加密，禁止放公开仓库。
- 保存最近 4–8 份备份，避免只保留单点。
- 每份备份记录：时间、执行人、文件位置、包含表、校验结果。

### 5.3 恢复要求

按 `docs/备份与恢复演练记录模板.md` 执行：

- 恢复到临时数据库或临时项目；
- 校验账号数、测试记录数、同意记录数；
- 用测试环境启动应用抽检；
- 记录 RPO / RTO；
- 未成功恢复前，不得把 E10 标记为完成。

## 6. 故障分级与响应

| 级别 | 示例 | 响应动作 |
| --- | --- | --- |
| P1 严重 | 应用白屏、数据库不可用、账号串数据、数据丢失、密钥泄露 | 立即登记，DEV + 运维介入，评估停用/回滚 |
| P2 较高 | 某页面异常、报告生成失败、某账号数据异常 | 当日处理，限定影响范围 |
| P3 一般 | 文案、布局、非关键提示问题 | 纳入补丁窗口 |

详细处置流程见 `docs/安全事件应急预案.md`。
